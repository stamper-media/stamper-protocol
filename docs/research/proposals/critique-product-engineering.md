# Stamper — Critique: product scope, UX and engineering cost

Critic: product + engineering-cost. Date: 2026-10-01. Inputs: `VERIFIED-SDK-FACTS.md`, the three proposals (`proposal-trustless-first.md`, `proposal-product-first.md`, `proposal-security-ops.md`), the research reports (`app-stack`, `codes-ux-legal`, `watermarking`, `filecoin-storage`, `fevm-contracts`, `trusted-capture`, `threat-model`, `perceptual-hashing`), and the actual state of `stamper` (pnpm 10.32 workspace; `packages/core` with synapse-sdk/viem/multiformats and `typescript ^7.0.2`; `contracts/` is still the Foundry `Counter` template).

Scoring frame (0–10): would a 2–3 person team ship a demoable, honest product on mainnet in one quarter by following this document, and would a confused user come away with the right belief? Trust-model correctness is judged elsewhere; here trust choices are penalised only when they cost engineer-weeks or confuse users.

Effort yardstick: one engineer-week (ew) = one full-stack engineer for five days, including testing and the CI/EAS plumbing the proposals never count. Component estimates (shared wherever a component appears):

## 1. `proposal-product-first.md`

**What it gets right (and nobody else does as well).** It is the only document that designs the user's path with the clock running: "share-ready in ~10 s, resolvable in ~2 min, everything slower catches up visibly". Its §8.2 lists eight failure states as *designed screens* (Pending, Original temporarily unavailable, Withdrawn, Device revoked later, Several candidates, Mismatch, Invalid code, Not registered): the single most valuable product artefact across the three proposals. Keeping the QR *out* of the default badge (§6.1) is correct and evidenced: a scannable QR needs ≈ 12 % of the short side after a 1080 px downscale (watermarking §1.3), which is a poster, not a badge. Code `K3Q9-XA2M-7` (8 + 1 Crockford symbols) is the right human channel: nine symbols is what people type from a screenshot, and the same 40 bits are the TrustMark `BCH_SUPER` payload. The MVP key choice (software secp256k1 in SecureStore, App Attest / Play Integrity bound to the claim digest and checked server-side, P-256 paths *implemented and fork-tested in the immutable contract but unused by clients*) is the lowest-risk way to ship without custom native code while keeping the door open. `bindStorage(Binding[])` batches both copies into one tx; the empty-`pieceCid` path for video avoids the unknown cost of a pure-JS fr32 tree over 500 MB on Hermes. The verdict ladder has concrete thresholds (PDQ ≤ 15 / 16–40 / none).

**Where it fails: the schedule is fiction and the MVP is three MVPs.** "MVP (weeks 1–6, demoable end to end on mainnet)" contains iOS + Android builds with photo *and* video, App Attest and Play Integrity, web capture at L0 with passkey *and* magic-link auth, registry + resolver on two networks, relayer, FOC upload of original *and* share copy, badge, TrustMark, **C2PA**, PDQ *and* vPDQ, the full verify page with eight failure screens, evidence JSON, a CLI, Compose, monitoring, and > 1 GiB video chunking (§6.6). By the table above that is 28–35 engineer-weeks; six calendar weeks implies five engineers in perfect parallel. Over-engineering inside the MVP line: C2PA (1.5 ew; until the Conformance listing every validator says "unknown source", so a user sees nothing); vPDQ (MVP video verification can be exact-hash only); web capture with two auth methods (the brief's "in-app" capture is the mobile app; the website's job is verification); chunking of > 1 GiB originals that the 5-minute cap already excludes.

**Code scheme gap.** The code is drawn by the issuer (CSPRNG) and the contract enforces only `code % 37 < 32` and uniqueness; the "refuse candidates within symbol-Hamming distance 1" rule lives in Stamper's database. The proposal also ships a self-submit path "from day one". A self-submitter therefore chooses their own code, and nothing on chain stops `K3Q9-XA2M-8`-style neighbours of an existing code, which defeats the check symbol's purpose (codes-ux-legal §1.5: "never allow vanity/user-chosen codes"). Either derive the code on chain or move the neighbour check on chain (security-ops has it: 248 SLOADs, cheap on Filecoin). Second gap: the app shows the code at the 202 ("the code is reserved") before the tx is included; if the relayer tx reverts for any reason the user has already shared a dead code. The Pending screen must not let the share sheet open until the receipt exists, or the design must accept re-issue and say so.

**Cost.** Its own table (§5.5) says ≈ $0.02 per photo first year, dominated by four piece-adds (original + share, two copies each). Half of that is the share copy, which is reproducible from the original + mark spec and is served from Stamper's cache anyway (§11: "previews are served first"). Storing the derivative on FOC in the MVP is pure cost and one more tx (`attachDerivative` is still needed, the *bytes* are not).

**UX misreads it does not address.** The level word "Captured in the Stamper app" at L1 is attached to a software key whose attestation was checked by Stamper's server; the chain only verified a secp256k1 signature. That is fine for the MVP, but the verify page's "Chain proof" panel must say "device attestation checked by Stamper at upload" and not imply the chain verified the attestation. Also unaddressed: Android uploads only progress while the app is foreground (app-stack pitfall 12); the "share-ready in 10 s" promise assumes the user did not background the app.

**Repo and tooling.** It is the only proposal that notices `packages/core` pins `typescript ^7.0.2`, which has no programmatic API until 7.1 and breaks typescript-eslint and `jest-expo`; pin `~6.0.3` workspace-wide. The monorepo layout (core / contracts-abi / verify-cli / mobile / web / api / worker / ml / tooling) is clean. Two worker replicas plus a 4-CPU ML limit on an 8-vCPU box is the right shape. `offen/docker-volume-backup` to an S3-compatible bucket is simpler than the other proposals' Garage.

**Score: 7.5 / 10.** Best UX, lowest React Native risk, best failure-state thinking; loses points for a 2× understated schedule, an MVP padded with C2PA/vPDQ/web-capture/chunking, and the off-chain neighbour rule under a self-submit path.

## 2. `proposal-security-ops.md`

**What it gets right.** The "what breaks first, in order" list (§13 tail) and the public per-data-set storage-health page are the best operational thinking in the set; they are exactly the things an operator of one VPS needs on day two. The contract is the cleanest of the three: fixed `Binding[4]`, `effectiveLevel(stampId)` for post-revocation display, `codeIsFree(code)` as a view, `_noNeighbour` on chain (so the distance-2 rule is enforced regardless of who submits), `bindStorage` re-checking `findPieceIdsByCid` and `pdpEndEpoch` so a lying binder cannot bind the wrong bytes. The session key with `AddPieces` only and a 7-day expiry is the right custody shape. The 72-hour offline deadline and "attested on upload" labelling are honest. Rejecting per-user data sets with the actual numbers (0.12 USDFC/month flat + reserve + a Filecoin account per user) is correct.

**Where it fails: the operational footprint contradicts "one VPS, small services".** The Compose file has twelve containers: caddy, web, api, worker ×2, relayer, ml, attest-android (JVM), indexer (Ponder), postgres, mirror (Garage), prometheus, alertmanager. Three exist only because of choices made elsewhere: the JVM service because L1 on Android is defined (§1.3) to require Key Attestation chain verification *in the MVP*, although Play Integrity verdicts are themselves derived from Key Attestation since May 2025 (trusted-capture §0.1); Garage because the mirror is specified as an S3 API instead of a disk volume (app-stack §4.3); Prometheus + Alertmanager for metrics a `/metrics` endpoint plus a cron-driven ntfy check would cover for the first ten thousand stamps. The relayer is split into its own service with an AWS/GCP KMS signer, a cloud dependency in a one-box design; a Docker secret is the MVP answer. Each extra container is a Dockerfile, a health check, a backup and an upgrade path.

**Hardware P-256 in the MVP is the biggest schedule risk and it is not priced.** It needs (a) a Swift module calling `generateAssertion(keyId, clientDataHash:)` with raw digest bytes, because `@expo/app-integrity` hashes a string (trusted-capture §1 table), (b) a Kotlin `signWithAttestedKey` module because the Expo package exposes the chain but no signing, (c) DER → raw conversion on both, (d) `react-native-quick-crypto` with Nitro, (e) biometric-gated Keystore windows, and (f) an on-chain path whose gas is unmeasured, with a pivot to a self-deployed Daimo verifier that changes the constructor. That is +3.5–4.5 ew of the riskiest kind (native, two platforms, alpha dependency) before the first stamp exists. The document knows this (§13.1–3) and still puts it in the MVP.

**Code scheme: nonce grinding breaks offline capture.** `code40` is derived from `stampId`, which depends on the client-chosen nonce; the app "grinds nonces until the check value is < 32 and until `codeIsFree(code)`" via `eth_call`. Offline (§7.5 supports it) the app cannot call `codeIsFree`, so a queued claim can revert on `CodeTaken`/`CodeNeighbour` days later, after the App Attest counter has moved on and the user has long since shared the badge the app predicted. On iOS the nonce *is* the assertion counter, so "grinding" means burning assertions, and a claim that must be re-signed after a revert gets a new counter and therefore a new stampId and a new code. The fix is simple: let the issuer (or self-submitter) choose a random code and keep the on-chain uniqueness + neighbour check; the code stops depending on the signature and offline queues become safe.

**MVP is Calibration-only.** "Demoable end-to-end on Calibration, ~8 weeks" is the most honest timeline here, but Calibration storage is not persistent (filecoin-storage §1.3 quoting the filecoin-pin README). A demo whose "original copy served from Filecoin" can vanish is not a demo of the product's one promise. Mainnet must be inside the MVP (it is cheap: gas is ≈ $0.00003 per tx and the data sets cost 0.12 USDFC/month each).

**Under-specified.** The private record is "encrypted with the per-stamp key (§11.4)" even in public mode, so sealed-mode key wrapping (device ECDH key + KMS) leaks into the MVP through the back door. Web L0 keys live in IndexedDB as non-extractable WebCrypto keys, which vanish on "clear site data"; nothing says what the user sees afterwards. Failure states on the verify page are a sentence, not a list. The browser must re-verify a P-256 App Attest signature from the event, which requires archival `eth_getLogs` on public RPC (its own §8.3 admits "~2,000 blocks of state") so in practice the page reads Stamper's DB for the signature, which is fine but should be said.

**Cost.** Six piece-adds per photo (original, marked, record × 2 copies) ≈ 0.02 USDFC plus 4 data sets at 0.12 USDFC/month. Same objection as above: the marked copy and the record do not need to be FOC pieces in the MVP.

**Score: 6 / 10.** Cleanest contract and best ops instincts, but the MVP carries twelve containers, two custom native modules, a JVM, KMS and a code scheme that fails exactly when the journalist is offline.

## 3. `proposal-trustless-first.md`

**What it gets right.** The independent-verification recipe (§8.3) in plain `cast call` and `curl` is the clearest statement in the set of what "trustless" means operationally, and the design decision to store the full PieceCID bytes on chain (≈ 40 B instead of a keccak) so the record is self-describing and can be passed straight into `findPieceIdsByCid` is worth grafting. The piece-metadata labels (`stamp`, `role`, `sha256`) make every FOC piece self-labelling in the FWSS event log. `stampByDerivativeHash` lets a byte-identical shared copy resolve without any perceptual guessing. Deriving the code on chain from `stampId` = the EIP-712 digest means the app can predict the code before submission with no issuer and no DB, and the only chain-dependent event is a collision at ≈ 3·10⁻⁹. The registry has literally no privileged role, which is the simplest possible governance story to explain to a user.

**Where it fails: the code and watermark do not fit each other, and the badge gets heavier.** The code is 11 + 1 symbols (`XXXX-XXXX-XXXX`, 55 bits) but the only robust invisible watermark carries 40 bits, so the proposal puts "the first 8 symbols" in TrustMark. The on-chain mapping `stampByCode` is keyed by the full 55-bit payload, so a watermark decode yields a *prefix* that cannot be resolved on chain; it needs Stamper's index. The document's own claim that codes "need no Stamper database to resolve" is therefore true for typed codes and false for the watermark path, which is the path that matters once a platform has stripped everything. On the badge, 12 symbols plus two hyphens at the ≥ 17 px cap height the research requires is ≈ 19 % of a 1080 px width versus ≈ 14 % for 9 + 2; the proposal's own risk #14 concedes "12 symbols is long for a visible badge". The justification is enumeration resistance, but every public stamp is enumerable from `CaptureRegistered` events anyway, and sealed stamps expose only hashes. Spend the bits on usability: 40 bits, on-chain uniqueness, on-chain neighbour check.

**Six transactions per stamp.** `registerCapture`, `bindStorage` × 2 (original on two providers), `registerDerivative`, `bindStorage` × 2 (marked copy). Each lands in the next tipset (30–90 s), each needs relayer nonce management and receipt polling with a reorg re-check, and the marked-copy pair exists only because the derivative is stored on FOC. Product-first's `bindStorage(Binding[])` does the same work in one call. Storing `sig` and `authData` in contract *storage* (not only in the event) so "the device signature can be re-verified from state alone" is defensible against archival-RPC limits but it is the kind of choice that should be priced (extra SSTOREs per stamp, dynamic `bytes` in the `Stamp` struct) and it is not.

**MVP scope.** "Out of MVP: C2PA, L2, video invisible watermark, sealed mode, direct-to-SP upload, OTS" is the right list of cuts, but what remains is still: P-256 on chain with App Attest `authData` reconstruction, two custom native modules (`modules/stamper-keys`, "≈ 100 + 150 lines", in practice 2–3 ew with CI and device testing), `react-native-quick-crypto`, an offline queue, ≤ 1 GiB video with on-device PieceCID of the whole file (benchmark unknown), capture records and attestation bundles as FOC pieces (public or encrypted, so key plumbing again), a Ponder indexer, a wallet self-submit page (wagmi 3.7 + connectors), `IndexPublished` PDQ events, the CLI, and a mirror. Roughly 30–38 ew. "Every Stamper server has a documented bypass" is admirable, but each bypass is a feature with its own UI and tests, and in the MVP none will have a user.

**UX.** The verify wording ("Unaltered since it was registered at epoch E from a key at level Lx") is the most precise and the hardest for a lay viewer; it needs product-first's two-line header on top. Failure states are implied by the storage panel, not enumerated. `GET /v1/stamps/{code}/original` 302s to the provider/FilBeam; for the first 1–3 minutes, exactly when the user is sharing, the only source is the mirror, and the page must say "served by Stamper, Filecoin proof pending" rather than silently falling back.

**Repo.** Layout mirrors product-first plus `services/indexer` and `services/attest-jvm` (v1). It keeps `typescript 7.0.2` for `tsc` and pins 6 only inside `apps/mobile`; two TypeScript majors in one workspace is a recurring source of "works on my package" bugs.

**Score: 5.5 / 10.** Strongest independent-verification story and several precise mechanisms worth keeping, but the 55-bit code is at odds with the 40-bit watermark and the badge, the per-stamp tx count is the highest, and the MVP carries native modules, P-256, 1 GiB video, records-as-pieces and an indexer at once.

## 4. Cross-cutting

### 4.1 The shared over-engineering: the marked derivative on Filecoin

All three store the share copy (two of them also the capture record) as FOC pieces with two copies, doubling or tripling the per-stamp one-time fee (0.003 USDFC per piece per copy; filecoin-storage §1.7 shows the per-piece fee, not bytes, dominates small files) and adding one to three transactions per stamp. The derivative is reproducible from the original plus a versioned mark spec, is served from Stamper's cache in every proposal, and its *hash* on chain (`attachDerivative` / `stampByDerivativeHash`, one SSTORE) gives all the user-visible value. MVP rule: only the device-signed original goes to FOC; derivative bytes live on the VPS disk; a FOC copy can be added later as one more binding without a contract change.

### 4.2 The shared under-specification: the first three minutes

Every proposal registers first (seconds) and binds storage later (minutes), which is right. None of them fully specifies what the user and the viewer see in between. Required: (a) the app's share sheet is enabled only when the server-marked file exists and the registration receipt is in; until then the screen shows "Registering on Filecoin… your code will be K3Q9-XA2M-7" with an explicit "do not share yet"; (b) the verify page for a registered-but-unbound stamp shows the original *from the Stamper mirror* with the line "served by Stamper; Filecoin storage proof pending (usually < 5 min)", not a storage panel full of dashes; (c) if the relayer tx reverts, the app receives a push and the code is re-issued with an apology, and the previous code never resolves; (d) Android keeps the app foreground during upload or warns that backgrounding pauses it (app-stack pitfall 12). Product-first has (a) and most of (b); the others have neither in writing.

### 4.3 React Native risk, ranked

Product-first: lowest (`@expo/app-integrity` behind an interface, viem on Hermes, `@noble/hashes` for photos, quick-crypto only for video, no custom native code, Skia preview optional). Trustless-first and security-ops: both require two custom Expo modules on day one, Nitro-based quick-crypto, mmkv, and an alpha attestation package whose `generateAssertionAsync` input hashing must be read from source before the on-chain `sha256(digest)` reconstruction can be fixed. MVP rule: *no custom native modules*; the immutable registry supports P-256 key types from the first deployment, and clients move to hardware signing in v1 once the `0x0100` gas number exists.

### 4.4 Code / QR scheme, decided

Take 8 + 1 Crockford symbols (`XXXX-XXXX-C`, 40 bits = the TrustMark payload), issuer-chosen with a CSPRNG (product-first), with uniqueness *and* the 248-neighbour distance-2 check enforced in the contract (security-ops `_noNeighbour` + `codeIsFree`), never derived from a nonce the device must grind (fails offline), never longer than nine symbols (badge legibility, typeability). Badge: pill with code and domain only; QR on the share card and verify page (product-first §6.1). Decoder normalises case, `I/L→1`, `O→0`, strips separators, rejects non-ASCII. Reserve first symbol `Z` for a future version.

### 4.5 Monorepo and package boundaries

All three converge on the right shape, matching the initialised workspace: `packages/core` (pure TS, zero Node built-ins, runs on Hermes/browser/Node), `packages/contracts-abi` (`@wagmi/cli` output), `apps/mobile`, `apps/web`, `services/api`, `services/worker` (same image, different entrypoint), `services/ml`, `contracts/`. Two corrections to the repo as it stands: `packages/core` must not depend on `@filoz/synapse-sdk` (Node/browser only); it should depend on `@filoz/synapse-core` and import only `/piece`, so the mobile bundle never pulls the SDK. And `typescript ^7.0.2` must become `~6.0.3` workspace-wide. `packages/verify-cli` and `services/indexer` are v1 packages.

### 4.6 Operational simplicity on one VPS

The MVP Compose file should be six services: `caddy`, `web`, `api`, `worker` (relayer inside; replicas: 1), `ml`, `postgres`, with four volumes (`staging`, `mirror`, `models`, `pg`) and one backup sidecar to an S3-compatible bucket. Secrets (relayer key, FOC session key) as Docker secrets; the FOC payer key never on the box (all three agree). Monitoring is a `/metrics` endpoint plus one cron job that runs the PDP/runway/relayer-balance checks and posts to ntfy; Prometheus, Grafana, Loki, Garage, a JVM verifier, Ponder, Goldsky and KMS are all v1 or later. Sizing: 8 vCPU / 32 GB NVMe (both product-first and security-ops agree; TrustMark on CPU ≈ 0.3 s/image, ffmpeg 1080p ≈ 1–3× realtime).

### 4.7 Cost per stamp, recomputed for the lean MVP

Photo (4 MiB original, two FOC copies, batched add-pieces, derivative on disk): one-time ≈ 2 × 0.003 + batch share ≈ 0.007 USDFC; storage ≈ 0.00002 USDFC/month; gas for `registerStamp` + one batched `bindStorage` ≈ $0.0001 budgeted (actual ≈ $0.00003). Roughly **$0.008 per photo in year one**, versus $0.02–0.03 in the proposals. Fixed: two data sets × 0.12 USDFC/month plus 0.10 USDFC reserve each; VPS ≈ $40–60/month; EAS Starter $19; Apple $99/yr. A 100 MB video ≈ 0.007 USDFC one-time + 0.0005/month. At 10 k stamps/month the whole bill is ≈ $150, of which Filecoin ≈ $80. The per-piece fee is the only lever; batching is the only tuning.

### 4.8 Effort, honestly

Product-first as written: 28–35 ew. Trustless-first: 30–38 ew. Security-ops: 32–40 ew (plus the mainnet step it leaves out). The lean MVP below: **15–19 ew**, two engineers for 8–10 weeks, with contract + mobile capture as the critical chain and the verify page in parallel.

## 5. What the MVP should contain, exactly

**Platforms.** Expo SDK 57 development builds for iOS (TestFlight) and Android (Play internal track); photo capture in-app; video capture in-app capped at 3 minutes / 500 MB (visible badge only, no perceptual video index, PieceCID computed server-side via the empty-`pieceCid` path). Next.js verify site. No web capture, no passkeys, no magic links (v1).

**Keys and levels.** Software secp256k1 key in `expo-secure-store` (device-only, backup off), one per device. App Attest (iOS) and Play Integrity standard token (Android) at enrolment and per capture, bound to `sha256(claimDigest ‖ serverChallenge)`, verified by the API before relaying → level 1 ("Captured in the Stamper app; attestation checked by Stamper at upload"). Level 0 reserved. Contract supports `KT_P256_RAW` and `KT_APPATTEST` from deployment with `vm.etch` unit tests and a Calibration fork test; a one-day wrapper measurement of `0x0100` gas is a week-1 task whose result is recorded, not acted on.

**Contract.** `StampRegistry` (immutable, OZ `EIP712` + `ECDSA`, registrar role held by one address, no timelock in MVP, 7-day announce in v1): `registerDeviceKey`, `revokeDeviceKey`, `registerStamp(claim, sig, authData, keyId, code)` with per-key nonce bitmap, deadline, `code % 37 < 32`, on-chain uniqueness and 248-neighbour check, `firstStampOf`, `StampRegistered` event carrying `sig`; `attachDerivative(stampId, derivedHash, markSpecHash)` (hash only, no PieceCID in MVP); `bindStorage(stampId, Binding[])` re-checking `getDataSetListener == FWSS`, `dataSetLive`, `getPieceCid` equality; views `storageStatus`, `verifyClaim`, `codeIsFree`. PieceCID stored as full bytes (trustless-first §3.1). `StampResolver` with `Flag` only. Deploy Calibration then **mainnet inside the MVP**.

**Code and badge.** `XXXX-XXXX-C`, 8 + 1 Crockford, CSPRNG by the API, displayed only after the registration receipt. Badge = dark pill, code, `stamper.app` text, 5 % of the short side, bottom-right, inside the 4:5 crop; no QR. Share card 1080×1350 with QR (`HTTPS://STAMPER.APP/V/K3Q9XA2M7`, V2-M). AASA + assetlinks for `/v/*`.

**Storage.** One Stamper payer (cold), `AddPieces`-only session key (30-day expiry) on the worker; two pinned approved providers, one data set each, `withCDN` on one; `synapse.storage.upload(original, { pieceCid, copies: 2, pieceMetadata: { stamp, role: 'original', sha256 } })` with batching on; `onPiecesConfirmed` → one `bindStorage` with both bindings. Original mirrored on the VPS disk (30 days) then an S3-compatible bucket. Derivative, preview and thumbnail on disk only. Retrieval order on the verify page: provider `/piece/{cid}` race → FilBeam → mirror, always re-hashed in the browser; the page says which source served the bytes.

**Marking.** `sharp` badge; TrustMark Q `BCH_SUPER` payload = the 40-bit code via the FastAPI sidecar; PDQ of original and share copy (pgvector HNSW). ffmpeg badge for video. No C2PA, no ISCC, no vPDQ, no video watermark.

**Verify.** `/v/<code>`: header (match outcome × capture tier sentence × permanent footer), compare slider + `pixelmatch` diff against a dropped copy, record panel (three times: device, Stamper receipt, chain epoch; finality included/safe/final), chain panel (viem `eth_call` via Multicall3, EIP-712 signature re-verified in the browser from the API-supplied `sig`), storage panel (`storageStatus` per binding, source used for the bytes). Upload-a-copy: exact sha256 (original or share) → TrustMark decode (server) → PDQ ≤ 40 confirmation → k-NN ≤ 31 → "no registered original found". The eight failure screens from product-first §8.2, plus "Filecoin proof pending" from §4.2 above. Evidence download = JSON. Independent verification = a documented `cast`/`curl` recipe in `docs/`; the CLI is v1.

**Backend and ops.** Hono API + BullMQ 6 on Postgres (no Redis) + drizzle; queues `ingest → register → mark → store → bind` plus repeat jobs `finality`, `pdp-monitor`, `runway`; six-container Compose on an 8 vCPU / 32 GB VPS; Docker secrets; nightly backups; `/metrics` + cron + ntfy. Offline capture: sign at capture, queue in mmkv, upload later, attestation at upload, 72-h deadline.

**Explicitly out of the MVP** (all v1 unless noted): hardware P-256 client signing and L2; custom native modules; web capture and L0 keys; C2PA; CLI; Ponder/Goldsky; sealed/encrypted originals; OpenTimestamps and RFC 3161; evidence PDF; takedown tooling beyond a resolver flag and a runbook; > 500 MB or chunked video; vPDQ/ISCC; self-custody data sets and wallet self-submit UI (the signed claim is exportable as JSON from day one, the UI is v1); Prometheus/Grafana, Garage, KMS, JVM attestation verifier; per-user data sets (never).
